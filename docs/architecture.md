# Архитектура Лари 2 / MVP 0.1

Лари 2 — не чат с нейросетью, а модульная веб-платформа для подготовки, анализа и проверки заявок ПФКИ.

Пользователь работает не с промптом, а с проектом: создает проект, отвечает на простые вопросы, выбирает модуль, получает результат и может вернуться к проекту позже.

## Слои системы

### apps/web

Frontend-интерфейс пользователя:
- Next.js;
- Tailwind CSS;
- shadcn/ui;
- крупный UX для аудитории 45–65+;
- пошаговые формы;
- карточки модулей;
- личный кабинет;
- страница проекта;
- отображение AI-результатов;
- отправка данных в backend;
- будущий cookie/session слой для авторизации и пользовательских настроек.

Frontend не обращается к GigaChat, SaluteSpeech и базе напрямую. Все секреты и AI-запросы идут только через backend.

### apps/api

Backend:
- FastAPI;
- принимает ответы пользователя;
- валидирует данные;
- собирает контекст проекта;
- выбирает модульный промпт;
- обращается к GigaChat через AI-router;
- позже принимает аудио/текст от SaluteSpeech;
- пишет данные в PostgreSQL;
- возвращает результат на сайт;
- хранит технические статусы запусков;
- не пишет пользовательские тексты и файлы в console.log.

### PostgreSQL

Основная база данных:
- пользователи;
- проекты;
- поля проектов;
- ответы пользователей;
- модули;
- запуски модулей;
- AI-результаты;
- статусы и ошибки;
- события пользовательского пути;
- платежи;
- промокоды;
- продуктовая аналитика;
- ссылки на загруженные файлы.

### File storage

Для MVP можно временно не реализовывать отдельное файловое хранилище, если нет загрузки файлов. Когда появятся файлы, они не должны храниться в console.log. Хранится сам файл или его извлеченный текст в управляемом хранилище, а в базе — file_id, user_id, project_id, module_run_id, размер, тип, статус обработки.

### Cookies / session

Cookies не являются основным хранилищем заявок. Они нужны для технических вещей:
- сессия пользователя;
- авторизация;
- “запомнить вход”;
- настройки интерфейса;
- согласие на cookie;
- аналитический идентификатор, если включаем аналитику.

Все содержательные данные заявки хранятся в PostgreSQL, а не в cookies.

## AI-поток

1. Пользователь отвечает на вопросы в web.
2. Web отправляет данные в api.
3. Api валидирует данные.
4. Context builder собирает контекст: паспорт проекта, ответы, правила модуля, ограничения по длине.
5. AI-router выбирает модель.
6. Backend обращается к GigaChat.
7. Ответ сохраняется в module_outputs.
8. Технический статус сохраняется в module_runs.
9. Web показывает результат пользователю.

## Речь

SaluteSpeech подключается позже как слой голосового ввода. Голосовой ввод не заменяет модули. Он помогает пользователю заполнять поля: речь переводится в текст, текст попадает в форму, затем обычный модуль обрабатывает его через GigaChat.

## Длинный контекст

Для больших текстов нельзя отправлять один хаотичный промпт. Система должна собирать контекст управляемо:
- базовый паспорт проекта;
- нужный пункт заявки;
- ответы пользователя;
- предыдущие результаты;
- правила ПФКИ;
- ограничения по символам;
- доказательства и источники;
- список рисков.

Большие документы позже обрабатываются чанками: сначала анализ частей, потом общий вывод.

## Console logs

В console.log не пишутся полные тексты заявок, загруженные файлы, персональные данные, полные промпты, AI-ответы целиком, ключи и токены.

В console.log можно писать user_id, project_id, module_run_id, статус, код ошибки, время выполнения, размер файла, тип файла и техническое сообщение без пользовательского содержания.

Для поддержки пользователей используется support/audit-хранилище в базе: по module_run_id можно посмотреть вход, результат, файл и ошибку, если это разрешено политикой обработки данных.

## Railway

В Railway должно быть три сервиса:
- Postgres;
- api с root directory `/apps/api`;
- web с root directory `/apps/web`.

API:
- Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`

Web:
- Build command: `pnpm install --frozen-lockfile && pnpm build`
- Start command: `pnpm start`

## MVP 0.1 считается готовым, когда

1. web открывается;
2. api `/health` работает;
3. api `/db/health` работает;
4. api `/docs` работает;
5. `/api/ai/test` возвращает ответ GigaChat;
6. есть первая страница Лари 2;
7. есть первый сквозной модуль “Паспорт проекта”;
8. данные отправляются из web в api;
9. результат показывается пользователю;
10. вход/выход модуля сохраняется в базе.
